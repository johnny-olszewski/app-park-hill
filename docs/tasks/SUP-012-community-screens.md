# SUP-012: Build the Community screens: home, browse and group detail

| Field | Value |
|---|---|
| Area | backend |
| Epic | EP-03 |
| Depends on | SUP-008, SUP-010, SUP-011 |
| Paired with | None |
| Status | Draft |

## Intent

Serve everything the Community tab shows from the backend, shaped for each person by what they may do, so wording, navigation targets and who sees what can change without a release.

## Scope

- `community.home` with exactly one of `group`, `my_groups`, `empty`; toolbar browse button for `groups.view_all`.
- `community.browse` (requires `groups.view_all`) with all groups, own groups badged, "No leader" badges, and a "Create group" toolbar button for `groups.create`.
- `community.group` with `GroupDetail`: details, leaders line, member rows with "You", leader icon, and per-row `remove` and `toggle_leader` only where allowed; `add_member`, `edit_fields`, `save`, Leave and Delete only where allowed.
- Community tab entry in `get_tabs` embeds `community.home` for the caller.
- All Community screens filter to community-type groups.
- Member rows carry no action until EP-04 adds `people.person`.
- All strings in migrations; per-persona fixtures generated from live output into `/contract/fixtures/community/<persona>/`.

## Out of scope

- Operations behind `call` actions (SUP-014).
- Picker and create screens (SUP-013).

## Acceptance criteria

| # | Criterion | Intent |
|---|---|---|
| AC1 | Each persona gets the correct home part: no group gives `empty`, one gives `group`, two or more give `my_groups` | The backend decides the state; the client only maps it |
| AC2 | "My groups" lists led groups first, then the rest, each by name | Ordering is backend owned |
| AC3 | Browse returns every non-archived group by name and is refused with `screen_unavailable` for users without `groups.view_all` | Stale buttons cannot reveal all groups |
| AC4 | `community.group` is refused with `screen_unavailable` for users who are not members, leaders or holders of `groups.view_all` | Access rules hold even with a direct link |
| AC5 | Each action and capability appears only for personas allowed to use it (checked per persona) | The UI is driven by what each person can do |
| AC6 | Changing a string or a navigation target in the database changes the next response | Wording and navigation are remote |
| AC7 | Per-persona fixtures are generated by one script and match live output | Mocks mirror the real backend per persona |
| AC8 | pgTAP tests cover AC1 to AC5 | Enforced, not documented |

## Technical notes

- One assembly function per screen key, reused by `get_screen` and `get_tabs`.
- Every function starts with `require_active_user()`.
